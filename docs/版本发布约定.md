# main、客户端与正式服统一版本发布约定

确认日期：2026-10-28。依据：用户明确要求“像这种，需要保持服务器和客户端版本统一，记录为md”。本约定取代此前“服务器与客户端发布版本独立递增”的做法。

## 统一发布版本

- 每次正式发布使用同一个发布版本号，必须满足 `SERVER_VERSION === CLIENT_VERSION`。
- 数值平衡、成长、技能、伤害结算、防御塔规则等调整，即使主要由服务器执行，也属于两端共同发布的版本。
- 界面、美术、启动器或服务端内部改动正式发布时，同样同步提升两端发布版本；不能仅升其中一端，也不能仅改 `RULESET_REVISION` 代替正式版本提升。
- 发布号必须高于两端已有正式版本；不回退版本号，不覆盖已发布的同版本内容。通常修复及数值微调提升补丁号，较大功能改动提升次版本号。
- 对齐 `shared/protocol.js`、根 `package.json` 与 lockfile、两端发布包的 `package.json`/`VERSION.json`、桌面应用版本和仓库 desktop-client.json 中的发布号。

## main 可运行与三方同步（2026-11-03补充）

依据：用户明确要求“以后 main、客户端和正式服版本必须同步，别再出现拉取最新版本却进不了游戏的情况”。`main` 是玩家的正式运行入口，未完成的发布工作保留在开发分支；不能以完成 Git 合并替代两端上线。

发布完成、任务交付以及非发布时段，以下发布号必须全部等于同一个版本 R：

| 核对对象 | 必须核对的实际内容 |
|---|---|
| 远端 main | 先 fetch，再读取 `origin/main:shared/protocol.js` 的 `SERVER_VERSION`、`CLIENT_VERSION`，以及根 package/lockfile 的版本。不能只看本地功能分支。 |
| 可拉取客户端 | `origin/main:desktop-client.json` 的 `version`/`serverVersion`、`client/prebuilt/client-version.json` 的客户端发布号，以及实际启动窗口的版本。启动文件及运行时分片哈希必须匹配。 |
| 正式服务器 | 实时读取 `/api/version` 和 `/api/health`，两处的 `serverVersion`、`clientVersion` 均须为 R。不能仅凭包目录名或历史部署记录判断。 |
| 实际可进入 | 从完整拉取的 main 通过根目录魔法王座.exe启动，使用既有账号验证登录、身份和 SSE 快照，确认没有版本拦截。 |

GAME_VERSION 和 PROTOCOL_VERSION 另外按兼容规则核对；它们不能代替发布号。纯文档、测试或辅助工具提交不改变运行内容时无需升版，也不因 main 多出文档提交而重复发布同一个版本。

### 发布是一条连续流程

1. 先在功能分支准备源码、统一版本、客户端预构建与启动清单，完成相关测试、服务端兼容预检、上传准备、账号备份和回滚准备。
2. 确认本次发布授权及正式服可操作。用户仅要求检查、提交或合并时，不能据此把 main 留在未上线的新发布号；发布准备保留开发分支。会话中已有明确上线授权时，按完整流程继续，无需重复确认相同授权。
3. 准备就绪后，在同一任务、同一连续发布窗口内执行“客户端合入 main → 从已推送提交的 Git blob 制作服务端包/差异包 → 同版本正式服激活 → 新客户端验收”。GitHub 来源校验要求客户端提交先于服务端激活，因此不能将这几步拆成各自完成的任务；验收前不通知玩家拉取或宣称发布完成。
4. 只安排一个正式发布者。并行任务使用独立工作树，不切换其他任务正在编辑的共享目录分支；发现 main、正式服或基准摘要已变化时，停止旧包激活，先合入已发布提交，重新核对版本并制包，禁止用刷新清单代替代码合并。
5. 交付前再次 fetch main 并读取正式服接口，逐项完成上表核对。记录实际发布源 SHA、版本、matchId、备份/回滚目录、包哈希及登录/SSE结果；只有全部一致且可进入才算完成。

### 失败与禁止事项

- 服务端未上线或验收失败时，本次发布仍未完成。继续处理失败步骤并恢复 main 客户端与正式服一致；确有外部阻塞时明确说明当前三方版本、不可用影响和待完成步骤，不能只报告“提交成功”。
- 不把拉取旧安装包、只改版本字符串或放宽版本门禁作为版本统一的修复；临时使用旧客户端不代表 main 已恢复可用。
- 不强推改写已发布历史，不回退/覆盖正式版本，不绕过 GitHub 来源和提交继承校验；需要回退逻辑时仍以更高的统一版本发布。
- 保留战局不兼容时停止并说明，不能静默切换到重开；账号与会话结构变化继续走常规部署要求。

## 兼容标记

`GAME_VERSION` 是两端共同使用的战斗兼容标记，`PROTOCOL_VERSION` 是 API、命令及快照结构兼容标记；二者不作为客户端或服务器各自独立的发布号。

发布号统一不要求每次递增兼容标记。战斗规则或共享行为改变导致旧客户端不兼容时，两端同时提升 `GAME_VERSION`；结构不兼容时同时提升 `PROTOCOL_VERSION`。`RULESET_REVISION` 只用于诊断追溯。

## 发布步骤与完成标准

服务端已支持[增量热更与战局选项](服务端热更.md)：兼容更新可只上传差异文件，并明确选择保留或重开战局。该方式继续遵守下列两端同版本、先客户端后服务端和上线验证要求。

1. 确定统一的新版本号，核对两端及 package/lockfile 一致；运行相关验证。
2. 构建客户端并运行 `npm run package:repository -- <桌面包目录>`，将源码、启动器、desktop-client.json、client/prebuilt 与所需运行环境一并提交，通过 PR 合入 GitHub 发布分支（默认 main）。同事拉取后应无需安装或构建即可启动。
3. 工作区保持干净，服务端包从已推送发布提交的 Git blob 生成，记录仓库、分支和完整 SHA。激活前重新验证 GitHub 内容与提交继承关系。
4. 先确保 GitHub 上的配套客户端可拉取，再备份正式账号并切换同版本服务端；不再生成、签名或上传客户端自动更新包。
5. 验证 `/api/version`、`/api/health` 两端发布号一致；旧版必须被拦截，手动拉取后的新版可登录并同步 SSE。旧 `/api/updates/` 接口返回410。
6. 记录版本、兼容标记、GitHub SHA、校验值、验证结果和回滚目录；交付前再次 fetch main、核对仓库客户端与正式服实时版本。三方全部一致且 main 实际客户端可登录并同步 SSE 后，才能报告发布完成。

自2026-10-29起按用户要求取消客户端自动更新。所有玩家退出游戏后手动拉取完整仓库，再运行仓库根目录的魔法王座.exe。该约定替代旧的客户端签名包发布步骤；服务端增量热更及 GitHub 来源校验继续保留。

具体连接、凭据和上传方式见[部署指南](../deploy/README.md)。本机如有 `docs/服务器连接与密钥.md`，运维前须优先读取该本机说明，使用已保存的凭据。
