# 客户端与服务器统一版本发布约定

确认日期：2026-10-28。依据：用户明确要求“像这种，需要保持服务器和客户端版本统一，记录为md”。本约定取代此前“服务器与客户端发布版本独立递增”的做法。

## 统一发布版本

- 每次正式发布使用同一个发布版本号，必须满足 `SERVER_VERSION === CLIENT_VERSION`。
- 数值平衡、成长、技能、伤害结算、防御塔规则等调整，即使主要由服务器执行，也属于两端共同发布的版本。
- 界面、美术、启动器或服务端内部改动正式发布时，同样同步提升两端发布版本；不能仅升其中一端，也不能仅改 `RULESET_REVISION` 代替正式版本提升。
- 发布号必须高于两端已有正式版本；不回退版本号，不覆盖已经发布的同版本签名包。通常修复及数值微调提升补丁号，较大功能改动提升次版本号。
- 对齐 `shared/protocol.js`、根 `package.json` 与 lockfile、两端发布包的 `package.json`/`VERSION.json`、桌面应用版本和更新清单中的发布号。

## 兼容标记

`GAME_VERSION` 是两端共同使用的战斗兼容标记，`PROTOCOL_VERSION` 是 API、命令及快照结构兼容标记；二者不作为客户端或服务器各自独立的发布号。

发布号统一不要求每次递增兼容标记。战斗规则或共享行为改变导致旧客户端不兼容时，两端同时提升 `GAME_VERSION`；结构不兼容时同时提升 `PROTOCOL_VERSION`。`RULESET_REVISION` 只用于诊断追溯。

## 发布步骤与完成标准

服务端已支持[增量热更与战局选项](服务端热更.md)：兼容更新可只上传差异文件，并明确选择保留或重开战局。该方式继续遵守下列两端同版本、先客户端后服务端和上线验证要求。

1. 确定统一的新版本号，核对两端发布号及相关元数据一致；运行与改动相关的验证。
2. 用同一批源码构建两端发布包；客户端即使没有界面变化，也要生成对应版本的完整包并签名。
3. 先上传并校验新版本客户端签名清单与完整包，再备份正式账号并切换服务端发布目录。
4. 验证 `/api/version`、`/api/health` 的 `serverVersion` 与 `clientVersion` 等于本次统一发布号；核对签名清单和可下载包版本一致。
5. 验证旧客户端发现更新、安装并连接新服务器，以及登录、战局配置和 SSE 同步。两端均完成验证后，才能报告统一发布完成。
6. 记录两端发布版本、兼容标记、规则修订、包校验值、验证结果和回滚目录。回滚时以配套的两端发布版本为单位恢复。

具体连接、凭据和上传方式见[部署指南](../deploy/README.md)。本机如有 `docs/服务器连接与密钥.md`，运维前须优先读取该本机说明，使用已保存的凭据。

## 约定建立时的历史记录

2026-10-28 的数值调整此前以服务端 `0.3.1`、客户端 `0.4.2` 发布，战斗兼容标记均为 `0.3.0`。这是本约定建立前的版本不一致状态，不符合新的统一发布要求。

以上仅记录约定建立时的状态，不作为当前线上版本声明。后续统一发布须选择高于已有两端版本的新版本号，并完整执行两端打包、签名、部署和验证流程；当前版本以正式服版本接口及签名更新清单为准。
