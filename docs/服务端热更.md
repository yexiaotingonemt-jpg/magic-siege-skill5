# 服务端增量热更与战局选项

本功能将更新后的运行代码切入当前 Node.js 进程，支持选择保留或重开战局。通过新发布目录加载完整的新模块依赖图，只传输改变的文件；未变文件在服务器本地复制或文件系统写时复制，旧版本保持完整，不在 current 内原地覆盖。

## 首次启用

旧服务没有控制通道，首次必须按照现有统一发布流程常规部署支持热更的版本，并更新 `bin/run-user-service.sh`。首次进程重启仍会重开战局，需安排维护时间。本功能不自动执行首次上线，也不会改动已有正式账号库。

启动脚本新增 `MAGIC_SIEGE_ROOT` 与 `MAGIC_HOT_UPDATE_SOCKET`；后续热更命令通过 `shared/runtime/hot-update.sock` 工作。该 Unix socket 和所在目录分别限制为 0600、0700，仅服务账号可访问。游戏公网接口不提供发布入口，游戏房主身份也不能发布代码。控制服务运行于 Linux/Unix，Windows 开发机可制作差异包。

## 两种战局选项

| 参数 | 行为 |
|---|---|
| `--battle preserve`（默认） | 保留同一个 matchId、玩家与英雄对象、成长、积分、体力、冷却、阶段计时、暂停/倍速、弹道、持续效果、待执行技能和指令去重记录；已有 SSE 连接和登录会话继续使用。 |
| `--battle restart` | 创建全新的战局和 matchId，清空本局成长、积分、单位与计时，采用新版本默认配置；保留账号库与登录会话，结束旧 SSE，让客户端重连到新战局。 |

“重开”是全新战局，不等同于原房主面板只重建地图的 `restart` 指令。

保留模式保留真实的运行对象及其引用关系，不使用面向客户端的裁剪快照恢复状态。新逻辑通过切换 Room、Simulation（含继承的技能规则）与 Accounts 原型生效；更新前已经排队的技能闭包继续执行其原回调，后续操作使用新实现。不承诺进程崩溃、断电后的战局恢复。

新默认配置会应用到后续读取中；房主已经修改的配置覆盖项保留。现存英雄/小兵的生命、攻击等实例属性不会强制重算，需按生成、契约或重开时机生效，避免中途改变现有单位状态。重开模式使用新默认配置。

## 发布前提与兼容性

- 继续遵守[统一版本发布约定](版本发布约定.md)：两端使用同一个递增发布号；先准备并校验配套客户端签名包，再切换服务端。服务器增量传输不替代客户端发布。
- `server/game-runtime.mjs` 中 `HOT_STATE_SCHEMA` 声明战局内存结构兼容性；改变对象结构、旧技能闭包无法兼容时必须提升该值。保留模式要求它、GAME_VERSION 和 PROTOCOL_VERSION 均与当前相同；不兼容时明确拒绝，不自动改为重开。
- 重开模式可接受新的战局结构及战斗/协议标记；账号与登录会话仍共享，`HOT_ACCOUNT_SCHEMA` 变化需常规部署。
- `server/index.mjs`、`server/hot-update.mjs`、`server/release-manifest.mjs` 和签名信任文件 `shared/update-protocol.js` 为进程引导层，改变这些文件需要常规部署。
- 新代码不得在模块顶层启动服务、修改旧战局或产生外部写入；构造函数/字段兼容性须由发布者通过测试确认。仅保持 schema 数字不变不代表任意代码都兼容。
- 每个进程最多执行 50 次热更，达到后安排常规重启，以控制 ESM 模块缓存的累计内存。

## 命令流程

以下命令在完整测试和两端打包完成后执行。`npm run package:server` 已自动生成 `server-manifest.json`，包含发布文件哈希与版本。

1. 在服务器上导出正在运行的版本清单：

```sh
node /home/colleague/apps/magic-siege-skill5/current/deploy/server-update.mjs status --root /home/colleague/apps/magic-siege-skill5 > /tmp/magic-server-status.json
```

将该 JSON 下载到本机辅助目录，例如 `E:/Codex/Support/magic-siege-support/references/active-server.json`。

2. 在开发机根据基准清单制作差异包（output 必须是不存在的新目录）：

```sh
node deploy/server-update.mjs pack --base E:/Codex/Support/magic-siege-support/references/active-server.json --source E:/Codex/Support/magic-siege-support/outputs/本次服务端包 --output E:/Codex/Support/magic-siege-support/outputs/本次差异包
```

输出目录仅包含 `delta.json` 和 `payload/` 下变化的文件；删除项记录在清单中。将整个差异包目录上传至服务器的 `incoming/`，无需上传未变文件。通过现有 SSH/SFTP 认证传输，凭据不写入包中。

3. 在服务器执行二选一命令：

```sh
# 默认保留战局
node /home/colleague/apps/magic-siege-skill5/current/deploy/server-update.mjs apply --root /home/colleague/apps/magic-siege-skill5 --bundle /home/colleague/apps/magic-siege-skill5/incoming/本次差异包 --battle preserve

# 明确重开战局
node /home/colleague/apps/magic-siege-skill5/current/deploy/server-update.mjs apply --root /home/colleague/apps/magic-siege-skill5 --bundle /home/colleague/apps/magic-siege-skill5/incoming/本次差异包 --battle restart
```

命令会锁定发布流程、核对基准和各文件哈希、在 `releases/hot-<UUID>` 构造完整版本，再请求本机运行进程切换。进程短暂停止战斗推进与新请求，等待已接收的请求完成；准备新代码并自检后，同步切换运行对象和 current 软链接，恢复请求与推进。节点进程和监听端口不重启，暂停时间不计入战斗推进。

4. 命令成功须返回 `ok:true`、`verified:true`，并包含变化/删除文件数、版本、发布摘要、原/新 matchId；继续按正式发布要求验证版本接口、登录、客户端与战局同步。部署记录保存在 `shared/runtime/hot-updates.jsonl`。

## 失败处理

文件或客户端校验失败、基准过期、编译/导入失败、状态不兼容均拒绝激活。激活阶段自检、目录切换或记录失败时恢复旧运行原型、配置及 current 指向；重开模式在成功前不会断开旧战局连接。未激活的新目录可保留用于排查，旧版本与账号文件不覆盖。

控制请求超时或连接中断不代表发布失败：先执行 `status` 对照摘要、版本和 matchId，再决定后续操作，勿直接重复发布。发布锁为 `shared/runtime/hot-update-deploy.lock`；异常终止后先确认没有发布任务，再人工清理失效锁。服务进程崩溃留下的 socket 会在确认没有活动监听者且属主一致时自动清理。

热更之后普通进程重启由 current 指向的新目录启动。恢复历史功能应以新的、更高两端发布号发布回退代码；运行过程中产生的战斗结果不会自动倒退。首次启用、引导层/账号结构更新仍按常规部署流程备份账号与安排重启。
