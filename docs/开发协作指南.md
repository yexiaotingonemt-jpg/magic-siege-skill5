# 魔法王座开发协作指南

## 1. 文档与项目范围

- [玩法规则](玩法规则.md)：已实现的完整玩法、流程、职业技能及结算规则。
- [数值配置表](数值配置表.md)：当前生效静态参数、单位、数值和配置键；程序常量单独列出。
- 本文：项目运行、模块边界、接口、参数生效时机及协作要求。

基准日期为2026-10-29，已正式发布0.5.0；本轮完整机制和数值见[升级词条与精英兵](rules/15-traits-and-elites.md)。规则依据`shared/config.js`最终配置、服务端模型及当前前端实现整理。讨论记录、旧设计说明和旧版模块不作为当前规则入口。

本次文档不包含玩家账号、密码哈希、登录会话或本地运行数据。当前配置表为启动默认配置，不包含房主在某一运行中战局的临时覆盖。

## 2. 安装与启动

工程已拆为 `client/`、`server/` 和 `shared/`，具体命令以[根目录README](../README.md)和[部署指南](../deploy/README.md)为准。

开发机执行 `npm ci`、`npm run build`，然后分别在两个终端运行 `npm run start:server` 与 `npm run start:client`。API默认5183，桌面窗口内部使用自动分配的本机端口，关闭窗口时退出本地服务。`npm run dev` 通过Vite本地代理开发界面，仍需要单独启动服务端。

玩家完整解压桌面客户端包，双击 `魔法王座.exe`。自动连接内置正式服务器（http://124.222.216.66:5183），玩家无需选择或填写地址，本机美术与脚本通过内部资源服务读取，关闭窗口即退出。玩家无需安装依赖。桌面开发先执行 `npm run setup:desktop` 安装Electron运行环境。

服务器仅部署 server、shared 与服务端元数据，账号由 KC_DATA_DIR 指向独立目录。两端正式发布号保持一致；客户端必须先提交预构建文件和启动清单到 GitHub 发布分支，再发布同版本服务端。所有人手动拉取完整仓库，旧版由服务器拒绝；不再上传客户端签名更新包。详见[统一版本约定](版本发布约定.md)。

## 3. 架构和代码入口

服务端是唯一战斗结果来源。每个进程创建一个`Room`和一个权威`Simulation`；客户端发送操作并显示快照，不独立执行战斗推进。

服务计时器每25毫秒检查一次累计时间，以0.05秒固定步长推进，即20Hz战斗模拟。正常状态约每200毫秒同步一次快照，即5Hz；暂停时仅发送低频心跳。客户端位置在快照之间插值，到达最新坐标后不继续外推位置；显示时钟最多外推0.3秒并乘战斗倍速，动作用同步时钟表现。

## 4. 网络接口与操作边界

| 接口 | 方法 | 主要用途 |
|---|---|---|
| `/api/version` | GET | 公开的客户端目标版本、战斗兼容版本与协议标记。 |
| `/api/health` | GET | 版本、修订标识、战局标识、序列及连接数。 |
| `/api/register` | POST | `name/password/side`创建账号并登录；`side`：0=进攻、1=防守。 |
| `/api/login` | POST | `name/password`登录已有账号。 |
| `/api/me` | GET | 当前会话公开账号信息及本局玩家编号。 |
| `/api/state` | GET | 获取完整同局快照及当前配置。 |
| `/api/events` | GET/SSE | 身份事件、状态快照及心跳。 |
| `/api/action` | POST | 提交当前账号操作。 |
| `/api/logout` | POST | 退出当前会话并关闭该账号连接。 |

所有游戏接口都需要匹配的 `X-Magic-Version` 和 `X-Magic-Protocol` 请求头，SSE可使用 `clientVersion` 与 `protocolVersion` 查询参数；公开版本、健康探测与签名更新下载除外。缺失或不匹配均返回409与 `CLIENT_UPDATE_REQUIRED`。账号接口以外的游戏操作还需要登录Cookie。命令结构为`{id,type,args}`；同账号相同命令ID返回已处理结果，不重复执行。服务端从会话取得操作主体，不信任客户端指定的来源玩家或英雄。

| 命令 | 参数 | 权限与效果 |
|---|---|---|
| `contract` | `unitId,classId` | 当前账号确认契约。 |
| `cast` | `skill`，0～3 | 当前英雄施法。 |
| `target` | `unitId` | 当前英雄手动目标。 |
| `chooseTrait` | `traitId,level,classId` | 选择当前英雄或无英雄时预览职业的合法候选，服务器验证本阵营职业、库存和等级。 |
| `upgrade` / `respec` | 已取消 | 返回失败，不消耗或重分技能点。 |
| `auto` | `enabled` | 只改变当前玩家自动施法开关。 |
| `reserve` | `unitId` | 当前玩家选兵保留标记；不等于完成契约或全局独占。 |
| `stamina` | 无 | 普通玩家可用，只给自己增加100体力。 |
| `bots` | `attackBots,defenseBots` | 仅房主；单方0～50，总数不超过99。 |
| `pause` | `paused` | 仅房主；暂停整个战局。 |
| `speed` | `speed`为1/2/4 | 仅房主；改变全局战斗速度。 |
| `level` | 无 | 仅房主；给自己补足当前职业升一级所缺经验。 |
| `restart` | 无 | 仅房主；重建战场并重算本阶段结束时间，不等同重启账号服务。 |
| `config` | `config`完整对象 | 仅房主；验证后替换同局配置。 |
| `refill` | 无 | 仅房主的兼容命令，将自己体力设为100；不等同增加100。 |

连接中断时客户端不继续提交本地战斗结果，恢复后以服务端快照为准。同账号多页面命令仍共用同一英雄、冷却、体力及构筑。

## 5. 机器人与辅助工具

默认双方机器人英雄数为0。房主可独立设置双方数量，不改变兵线总数。增加时生成所需机器人玩家，职业按本阵营开放职业顺序循环分配；减少时优先保留原列表前部机器人，其余英雄以“机器人离场”结算并退役。

机器人无存活英雄时尝试契约适配小兵；契约消耗自身正常体力。机器人和开启自动施法的玩家按3秒间隔尝试自动施法；目标和技能仍须满足正常施放验证。机器人从权威候选中选择词条，同样遵守品质和库存。自动施法的具体选招实现为`chooseSkill5`，见当前技能模块，不将按钮亮起视为自动立即必放。

自动施法每次只选一个技能：遍历四个槽位，仅保留正常施法计划验证通过、评分大于0的技能，选最高分；同分保留较小槽位。公共评分为“2+预选目标列表人数”，以下分支替代对应评分：

| 职业 | 专项评分 |
|---|---|
| 兽人 | 守护战吼/蓄伤壁垒：被敌人锁定7，否则0；救援：被救者生命低于50%为10，否则1。 |
| 战车 | 除连轰外：主目标是塔7，否则3；连轰区域至少2敌人为8，否则2。 |
| 领主 | 冲锋目标普攻距离大于2格为9，否则5；火盾自身生命低于80%为7，否则2；大招自身6格内至少3敌人为10，否则1。 |
| 火法 | 大招炙热至少4层为10，否则1。 |
| 精灵 | 净化8；群疗被选目标的缺血比例合计大于1为10，否则0。 |

辅助工具在640×1136主界面外显示：自身体力+100、自动施法、账号和连接状态；房主额外显示机器人数量、暂停、1/2/4倍速、自身升级、重开和完整配置编辑。手机端置于游戏界面下方。

## 6. 配置来源与修改方式

服务器启动直接使用`shared/config.js`导出的最终`defaults`。`shared/default-config.json`为对应展开快照，服务器不会自动读取该文件覆盖最终配置。

最终配置在基础配置之上按职业设计及修订展开，随后统一放大主动技能的伤害、治疗、相关输出系数和控制额度。直接编辑源码中较早的字面量时，须检查后面的覆盖与倍乘；不得将已展开数值再重复翻倍。

英雄和塔的基础攻击在配置模块初始化时由基准推导。房主运行中调整小兵攻击或生命不会自动重新计算英雄、塔的已展开攻击数值。

| 参数类型 | 使用时机 |
|---|---|
| 小兵生命、攻击、距离、移速等模板 | 新生成小兵采用；现存实例不整体重建。 |
| 英雄基础模板 | 下次契约采用；现存英雄不被统一重建。 |
| 防御塔模板、列数及排倍率 | 地图重建时采用。 |
| 波次总数、权重及出生参数 | 下次生成兵线采用。 |
| 技能参数 | 新技能计划及对应执行过程按其读取时机采用；已锁定/已缩放效果不承诺回写。 |
| 机器人数量 | 应用后同步增减。 |
| 阶段时长 | 现有结束时间不立即重算；下一阶段或房主重开采用。 |
| 地图及普通行动参数 | 后续计算、移动和视野读取新值；不会为现存对象额外执行一次整体重置。 |

房主应用配置只保存在服务进程内，重启后恢复启动默认值。需要团队共享及持久采用的改动应回填代码/默认配置快照并提交版本库。

数值Excel中的黄色调整列为空表示沿用当前值，0表示明确改为0；百分比使用Excel实际百分比输入。回填时须按原键区分：`power=1200`代表1200%攻击，而`damageReduction=0.35`代表35%；两者的原始存储单位不同。

塔守护、20格手动距离、技能加点门槛及收益基准等为程序常量，修改配置JSON不能替代修改其代码来源。

## 7. 验证与协作流程

```sh
npm test
npm run build
npm run test:browser
```

模型及HTTP测试覆盖技能、成长、账号、权限、命令去重、手动目标、减攻速、射程抵达、冲锋回弹等。浏览器测试在隔离服务与临时账号目录完成五账号同局及手机界面检查，默认5194端口。

`playwright.config.js`的Chrome路径为Windows本机路径；其他开发环境须调整可执行文件路径。专项脚本位于`scripts/verify-*.mjs`，其中涉及截图、临时服务或浏览器启动的路径同样须按实际环境核对。

提交时将规则、数值、说明和相应验证保持同一口径：

1. 为改动创建独立分支，明确改动所属规则模块。
2. 修改权威实现及必要的数值源；显示性说明同步修改`ability-descriptions.js`等实际入口。
3. 补充能证明规则结果的模型或HTTP回归；涉及目标选择、特效、手机交互和联机表现时执行相应浏览器验收。
4. 更新对应玩法规则章节、静态配置表和开发入口，删除被替代规则的重复描述。
5. 提交变更和验证结果，经代码评审后合入，不把本地账号及运行数据提交仓库。

建议仓库忽略`node_modules/`、`dist/`、`data/`、`.env*`、`evidence/`、`test-results/`及本地日志。应提交运行所需源码、`client/public/`资源、`package.json`、`package-lock.json`、自动化测试和本组文档。发布内部协作仓库时使用私有可见性，由仓库拥有者分配成员权限。

## 8. 实现边界

项目为单进程、单房间、内存战局；账号持久化于账号文件，会话保存在内存。没有独立匹配、多房间、跨服务合局、战局持久化恢复或账号找回接口。

正式运行与验证采用不同数据目录；不复制现有`data/accounts.json`作为团队示例，不把账号名、密码哈希、Cookie或登录令牌写入文档。

旧机器人预设、未开放职业、旧版技能描述文件及部分保留参数不构成当前规则；`targetRecheckInterval`和`heroPriorityDistance`未被当前寻路读取，名义强度`strength`不直接乘算战斗属性。

文档与实现出现不一致时，先以当前实际调用链定位行为，再在同一变更中明确修正规则或代码；不得只改展示文字来宣称逻辑已改变。

## 9. 交接检测项

以下为静态审查发现的边界，未作为玩法规则设计，也未在本次文档工作中修改代码：

- `Simulation.resetMap`清除场上对象和持续字段，但不清空待执行`jobs`，也不把旧英雄对象统一标记为死亡。重建前已排队的前摇回调可能在新地图继续执行，需复现并确定重建取消策略。
- 全塔全毁时，模拟内先重建地图，同一步房间阶段检查又可能执行一次重建。最终场上保留后一次生成结果，但波次统计及日志可能重复增加，需单独验证。

处理这些边界时应新增隔离回归并明确阶段切换行为，不能将文档概述直接当作已修复实现。

## 超级账号与重开本局（0.5.5）

超级账号由服务器数据目录的 `super-accounts.json` 维护，内容为已有账号内部 ID 的 JSON 数组。运维备份后原子替换此文件，下一次认证请求立即生效；注册、登录参数不能设置超级权限。该文件与账号库一起保留在发布目录之外，不随客户端分发。

超级账号拥有房主体验工具权限，并额外开放 `POST /api/action` 命令 `{id,type:"restartMatch",args:{}}`。客户端“联机体验工具 → 重开本局”需要确认，确认后更换 matchId，清空全部玩家本局成长、积分、体力消耗、技能冷却、单位、阶段和计时，暂停及倍速恢复正常；保留当前配置、阵营、账号、会话和在线连接。初始体力由当前配置决定。旧 `restart` 仅重建战场并保留成长，界面改名“重建战场”。同账号同命令 ID 不重复重开。

正式权限授予 yxt 的已有内部 ID，避免通过改名或注册同名账号取得权限。权限撤销同样编辑服务器名单，公网不提供授予权限接口。
